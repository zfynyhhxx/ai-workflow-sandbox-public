# ADR-0001：受控产物连接层与既有工具边界

状态：实施依据为用户本轮明确授权；后续任务与高风险计划仍逐项批准。
日期：2026-11-12

## 背景与取舍

原起步包只提供 route/prepare，AO 不原生理解七角色、Tier、费用账本和人工批准。直接把任意 Issue 文本拼进 shell 或给 Worker 提供宿主凭据不可接受。

## 决策

- 使用标准库薄连接层负责验证、批准、调度与证据，不自研通用 Agent Harness；所有模型调用仍经过原生 CLI。
- API Worker 使用无外网命名空间和 Unix socket 桥接，只能访问计量控制面允许的 API 路径。Key 不进入 Worker。
- Builder 返回结构化文件产物，可信控制面验证批准路径后写入专用 worktree；不让模型取得 GitHub/审批控制权。
- GitHub 是任务与合并门禁权威，私有 SQLite 仅保存运行元数据。采用轮询与幂等处理，避免为本机试点公开 webhook。
- 正式和测试 Profile 分离；本轮使用 DeepSeek 兼容接口测试 Claude Code，不改变正式模型映射。
- 公开练习库使用新的无旧历史基线与 noreply 身份；原私库不变。

## 风险与恢复

未知请求保留最大预算；超时可能仍计费。重启不清零费用。恢复先检查 PID 与启动时间，不复用失效审查或输入变化的产物。worktree 与失败证据保留，禁止清理用户数据。
## 审查证据补充

实际练习发现，仅向 Reviewer 声明“检查通过”无法证明验收文件由控制面写入，也不足以证明当前冻结候选已验证。复用一个纯 Python 动态检查 core，分别由统一开发入口和无外网/无凭据隔离门禁调用；静态扫描与 Git 检查仍在可信控制面执行，不为运行验证入口而扩大隔离挂载。

Reviewer 上下文包含完整门禁摘要与 tree/记录哈希、模板来源/候选 blob 对照、有效批准摘要和权威文档。旧审查拒绝保持不变；修复更新规则后必须由人重新批准任务。report 承载信息说明，findings 只承载未解决问题，但控制面不删改模型 finding 或降低发布条件。
